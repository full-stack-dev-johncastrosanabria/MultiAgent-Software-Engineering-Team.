# Benchmarks

Benchmark runners and their inputs live under this directory. The multistack runner supports the cases `ingresos`, `interview` and `northgate`.

```sh
python3 evaluation/benchmarks/multistack/run_trial.py --help
```

Other runners: `ghcycle/run_cycle.py` measures the full GitHub cycle against real repositories and `ghcycle/probe_shallow_push.py` probes a push from a shallow clone. Scored results go to `ghcycle/results/`; raw reports go to the git-ignored `ghcycle/results/raw/`. Unversioned (v1) results score `infrastructure` and `delivery` as passed on a dry run without exercising them (see `docs/audit160926/02-evidencia-y-metricas.md`); from schema v2 those stages read as not exercised instead (below). `adr14/`, `adr16/`, `adr17/` and `adr18/` verify those decisions against a real Docker daemon; decisions 16–18 write their evidence to `results/`, while the decision 14 trial reports live in `../reports/runs/adr14-trial-*`.

A scored result's schema is versioned by convention, not by an ADR. An artifact with no `schema_version` key is **v1**: it does not record the ASET commit, specification, test specification or model chain, and `stages.clone.passed` is `bool(evidence)` — a report was written at all. `schema_version: 2` (present on every artifact `run_cycle.py` writes from this task onward) requires the same report **plus** a recorded target SHA: `stages.clone.passed` is `bool(evidence)` *and* `evidence.get("target_repo_sha")`. v2 can therefore only turn a v1 pass into a fail — a report exists but carries no `target_repo_sha` (an older CLI) or an explicit `null` (a current CLI whose lookup came back empty) — never the reverse, since anything that satisfies v2 already satisfied v1. This does **not** fix the case that motivated it: the CLI persists its report only once, at the end of a completed run, so a run that dies partway through (hung, killed, crashed) leaves no report under either schema, and neither version can tell a died-after-clone run from a died-before-clone run. What v2 adds is a name for that case — `stages.clone.detail` says the run wrote no report, distinct from both "predates this schema" and "no SHA was obtained" — not a resolution of it; resolving it means the CLI persisting clone evidence before it can die, which is outside this task's scope.

`schema_version: 2` also adds, at the top level: `aset_sha` (the ASET commit `run_cycle.py` itself ran from, read just before the run starts), `aset_dirty` (read at the same moment: `true` when that checkout had a tracked change anywhere or an untracked, non-ignored file under `src/`, `false` when clean, `null` when the check itself could not be answered — never conflated with "clean"; untracked files elsewhere, such as this benchmark's own `results/*.json`, do not count, so an untracked file outside `src/` that a run still reads is a known gap) and `aset_changed_during_run` (both values are read again after the run: `true` when either differs, `false` when all four readings match, `null` when a reading is missing on either side — so a commit, amend or branch switch during a run never lets `aset_sha` name code that did not run; the subprocess that runs the target project is launched with `PYTHONPATH` pinned to this same checkout, so `aset_sha` names the code that actually executed even when `run_cycle.py` is invoked from a worktree sharing a `.venv` with another checkout), `specification`, `test_specification`, `model_chain` (per `AgentRole`, `"exercised"` from `evidence["model_usage"]` or `"configured"` from `CloudRouter.selection_chain` for a role that never ran), `started_at`/`finished_at`, `target_repo_sha`, `stop_cause` (copied verbatim from the report, never reconstructed from error text; when the CLI wrote no report, it comes from the exit status instead: `infrastructure_unavailable` for `INFRASTRUCTURE_EXIT_CODE` (3, `contracts/enums.py`), which the CLI uses when a step that asks the infrastructure something failed before the graph — the pre-run Docker sweep got no answer, `docker compose config` could not read the project's compose file (it failed to run, timed out, rejected the file or returned no model), bringing the dependencies or the run daemon up failed (a refused second concurrent run on the same project included) — and `crash` for any other non-zero exit, including a compose file that compose did read and ASET itself refused: its isolation policy (a mounted runtime socket, `privileged`, `network_mode`, an external network or volume, volume driver options, a bind outside the checkout, a network or volume name its override cannot write) or an ambiguous or conflicting mapping of a component onto the compose services), `environment_failure` (an environment/infrastructure failure — a bind mount or other dependency ASET needs failing to come up — distinct from a failure of ASET itself and from why the run stopped; `cli_exited_infrastructure_unavailable` says it was read from that exit status rather than from a report), and `review_status` (`APPROVED` / `REJECTED` / `NOT_EXERCISED`, so a run the Reviewer never reached is not conflated with either verdict). A v1 report's `stages.clone.passed` and a v2 report's mean different things for the same reason any two schema versions can, which is exactly why the two are told apart by `schema_version` rather than left to look alike. The 18 unversioned reports in `ghcycle/results/` and the 27 raw reports in `ghcycle/results/raw/` predate this field; they are not rewritten or re-scored, and under this convention they read as v1.

In schema v2 every stage carries `exercised`. A stage the run never exercised has `passed: null` — neither a pass nor a fail: `delivery` on a dry run, and `infrastructure` on a dry run whose report records an infrastructure prerequisite (nothing was delivered) or on a run with no report at all (the prerequisite was never determined). A recorded `null` prerequisite is a legitimate pass, dry run or not. `clone`, `execute`, `spec` and `hygiene` are always exercised. `all_stages_passed` keeps its strict v1 name — every stage exercised and passed — so a dry run always reads `false` there; `all_exercised_stages_passed` judges only what the run exercised and decides `run_cycle.py`'s exit status, so a green dry run still exits 0; `stages_not_exercised` names the stages left out, and the printout marks them `SKIP … (not exercised)` rather than `PASS`.

Case specifications are in `multistack/cases/`. Stable baselines, provider probes and the `multinetwork` compose fixture remain beside the runner because they are benchmark inputs. Do not move or edit them as ordinary documentation; changes alter an evaluation contract and require the benchmark tests to be reviewed.
